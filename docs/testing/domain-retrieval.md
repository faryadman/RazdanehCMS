# واکشی و انتخاب دامنه

مبنا: `486b038` در شاخهٔ `jobs`. تاریخ گزارش: ۲۰۲۶-۱۰-۲۰ به وقت تهران. کاربر خطای NotFoundException در DomainService.ChangeDomain و JobHandler را گزارش کرد و اصلاح واکشی و مرتب‌کردن repository دامنه را خواست. وضعیت دیتابیس تولید بررسی نشده است؛ یافته‌های زیر از کد و SQL Server یک‌بارمصرف‌اند.

## یافته‌ها و اصلاح

| یافتهٔ قطعی | رفتار اصلاح‌شده | شاهد آزمون |
|---|---|---|
| ListInactiveDomain همان فهرست فعال را برمی‌گرداند | query مجزا برای غیرفعال و حذف‌نشده | Inactive_list_contains_only_inactive_non_deleted_domains |
| GetNewDomain کل جدول را می‌خواند و اولین ردیفِ بدون ترتیب را انتخاب می‌کند | انتخاب TOP(1) با فیلتر SQL، کنارگذاشتن نام خالی، تقدم زون آماده و سپس Id | Rotation_skips_blank_domain_names و Rotation_selects_one_ready_domain |
| catchهای ChangeDomain و ChangeTcp خطای سرور/Cloudflare را به غیرفعال‌بودن دامنه تبدیل می‌کنند | خطای اصلی و cancellation حفظ؛ پیام مستقل برای خالی‌بودن pool | Server_lookup_errors و Provider_lookup_errors و Provider_cancellation |
| ZoneId سرور در تعویض معمولی تغییر نمی‌کند؛ TCP دوباره همهٔ دامنه‌ها را می‌خواند | ZoneId همان دامنهٔ انتخاب‌شده ثبت می‌شود و query تکراری حذف می‌شود | Rotation_selects_one_ready_domain_and_copies_its_zone_to_the_server |
| هر نام پنج‌حرفی با تولید ۲۶ به توان ۵، یعنی ۱۱٬۸۸۱٬۳۷۶ رشته ساخته می‌شود؛ فقط اولین مورد مصرف می‌شود | ساخت مستقیم یک نام پنج‌حرفی با RandomNumberGenerator و حذف GenerateWordExtention | assertion قالب نام در تست‌های rotation؛ عدد قبلی از حلقهٔ بازگشتی به دست آمده و benchmark حافظه نیست |
| lookup زیردامنه، پایهٔ مصرف‌شده را به‌علت IsActive=false پیدا نمی‌کند و تعداد labelها را سه فرض می‌کند | lookup دامنهٔ ثبت‌شدهٔ حذف‌نشده با بلندترین suffix کامل؛ پشتیبانی از پایهٔ مصرف‌شده و دامنهٔ چندبخشی | Subdomain_rotation_can_reuse و Subdomain_lookup_matches و A_soft_deleted_base |
| ثبت زون می‌تواند ویرایش هم‌زمان مدیر را بازنویسی کند | UPDATE شرطی روی Id، نام قبلی، فعال/حذف‌نشده و زون خالی؛ بازخوانی تازه در شکست شرط | Zone_sync_preserves و Zone_sync_does_not_restore و Zone_sync_never_attaches |
| پاک‌سازی غیرفعال‌ها هر ردیف را جدا واکشی/حذف/ذخیره می‌کند | یک DELETE با شرط IsActive=false و انتقال cancellation | Cleanup_uses_one_delete و تست انتظار cleanup سرویس |

queryهای اختصاصی در `DomainRepository` هستند؛ خواندن‌ها AsNoTracking و مرتب‌اند و repository مالک context تزریق‌شده نیست. InitZoneId و CheckZoneId یک مسیر دارند. dictionary و configuration بلااستفاده، queryهای تکراری، کد unreachable و helper بازگشتی حذف شدند. ICloudflareApiClient مرز تست سرویس است؛ فراخوانی‌های بدون مصرف GetZones و بررسی دوبارهٔ وجود CNAME حذف شدند.

## قرارداد و راه‌اندازی

GetByFilter با ۰، ۱ و مقدارهای دیگر، مطابق رفتار legacy فهرست فعال می‌دهد؛ فهرست غیرفعال endpoint مستقل دارد. route، signature اکشن‌ها، DTOها و serializer تغییر نکرده‌اند. دادهٔ ListInactive اکنون مطابق عنوان آن اصلاح شده است. دامنهٔ پایهٔ جدید فقط از فعال‌ها انتخاب می‌شود؛ غیرفعال‌شدن پس از مصرف به معنی امکان استفادهٔ مجدد آن برای یک سرور جدید نیست. lookup سرور موجود می‌تواند همان پایهٔ مصرف‌شده و حذف‌نشده را بخواند.

اگر pool واقعاً خالی باشد، برنامه دامنهٔ واقعی اختراع نمی‌کند: باید دامنهٔ معتبر در پنل اضافه و دسترسی حساب Cloudflare به زون بررسی شود. زون خالی پیش از نوشتن DNS واکشی می‌شود. نبود زون، خطای مشخص دارد و دامنه مصرف یا سرور به‌روزرسانی نمی‌شود. سیاست Failed/NeedsReview زمان‌بند تغییر نکرده است؛ پیش از review یا درخواست مجدد، اثر احتمالی اجراهای قبلی بررسی شود.

## نتیجهٔ اجرا

۱۵ حالت SQL پیش از اصلاح اولیه شکست خوردند. سه حالت زیردامنه نیز جداگانه پیش از اصلاح آن مسیر شکست خوردند و حالت حذف‌شده از ابتدا رد می‌شد. اجرای کامل نهایی: ۷۴ تست unit/HTTP/قرارداد و ۷۱ SQL، مجموع ۱۴۵ تست .NET، به‌علاوهٔ ۱۳ JavaScript؛ همه موفق و صفر skipped. ۲۴ حالت جدید دامنه به suite SQL اضافه شده‌اند. هر ۲۸ snapshot و فایل‌های DTO نسبت به `657019e` بدون تغییر بایتی‌اند. build هشت پروژه با ۳ warning قبلی و صفر error و EF بدون pending model change موفق بود. تست‌ها سرویس Cloudflare بدل دارند و هیچ DNS زنده، اتصال تولید، Program اصلی یا seed اجرا نشده است.

## محدودیت‌ها

این گام بازطراحی مالکیت و حذف رکوردهای Cloudflare نیست. الگوریتم‌های قدیمی حذف گستردهٔ CNAME، update پس از حذف رکورد و تفسیر content به‌عنوان تاریخ همچنان نیازمند اصلاح و تست مستقل‌اند؛ موفقیت تست سرویس با provider بدل، صحت آن‌ها را اثبات نمی‌کند. خطای واقعی provider اکنون در مسیر تعویض دامنه به پیام گمراه‌کنندهٔ غیرفعال‌بودن دامنه تبدیل نمی‌شود.

قفل engine جدید، درخواست‌های مستقیم قدیمی پنل را قفل نمی‌کند؛ رزرو اتمیک pool میان چند درخواست دستی و DNS exactly-once در این گام ایجاد نشده‌اند. پاک‌سازی فیزیکی دامنهٔ مصرف‌شده، رکورد ثبت‌شدهٔ لازم برای lookup بعدی آن را حذف می‌کند؛ سیاست نگهداری پایه‌های درحال‌استفاده نیازمند تصمیم جداست. بازگشت کد این اصلاح migration ندارد و دادهٔ حذف‌شده با rollback کد بازنمی‌گردد.
